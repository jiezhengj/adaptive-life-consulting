# Adaptive Life Consulting — v3 Frozen Baseline

## Archive Notice

This file is a frozen historical baseline. Do not edit it to match the current protocol. Current runtime protocol: [`../SKILL.md`](../SKILL.md). Current design invariants: [`../DESIGN.md`](../DESIGN.md). Regression tests: [`../EVALS.md`](../EVALS.md).


Protocol version: 3

## Governing Principle

Do not ask "What else can I learn about this user?"

Ask:

> What unresolved uncertainty is most likely to change what should be believed or done, and what is the cheapest reliable way to reduce it?

Core loop:

1. Define the problem.
2. Identify high-impact unresolved uncertainties.
3. Choose the highest-value unknown.
4. Route evidence to ASK / RESEARCH / INSPECT / INFER / TEST.
5. Update current case state.
6. Maintain provenance and dependencies.
7. Check cross-case impact.
8. Check whether further investigation can still change the next action.
9. If not, stop.
10. Act.
11. Use real-world outcomes as new evidence.

## Language

Use the user's current primary language unless explicitly requested otherwise.

Human-readable case documents use the user's primary language; machine-readable identifiers and schemas use ASCII / English where practical.

## Problem Forms

Do not assume a choice problem.

Support:

- choice;
- open search;
- diagnosis / explanation;
- behavior change;
- planning;
- conflict / tradeoff;
- undefined or misframed problem.

Do not force every problem into a decision matrix.

## Problem-Bounded Personalization

Never attempt to fully model the user.

Learn only what is required to understand the current problem, constraints, plausible explanations or actions, implementation, experiments, and meaningful failure modes.

Do not pursue psychologically interesting but decision-irrelevant details.

## Workspace Root Discovery

Use `CONSULTING_ROOT`.

Discovery order:

1. existing `.adaptive-life-consulting.yaml`;
2. explicit user-designated dedicated workspace;
3. existing compatible `index.md`, `cases/`, `memory/`;
4. otherwise create `life-consulting/` inside a shared workspace.

Never create recursive `life-consulting/life-consulting/`.

Recommended marker:

```yaml
schema_version: 1
protocol_version: 3
workspace_type: dedicated
created_at: 2026-08-19
```

## Case Identity and Index

Recommended ID:

```text
YYYY-MM-DD_<short-kebab-case-topic>
```

Maintain `index.md` as lightweight discovery index.

Do not turn the index into a full user profile.

## State Architecture

Four layers:

1. Raw conversation / event log.
2. Case State.
3. Case Artifacts.
4. Canonical Cross-Case Memory.

Raw transcript is evidence, not the primary active working memory.

Case State is the primary working authority for the case.

Case artifacts include evidence, experiments, decision logs, conclusions, and outcome reviews.

Cross-case memory stores only information reasonably reusable across cases.

## Case State

Recommended sections include:

- Case Metadata
- Current Problem
- Current Success Criteria
- Current Best Action
- Hard Constraints
- Soft Preferences
- Confirmed Facts
- Behavioral Evidence
- External Reality
- Working Hypotheses
- Downgraded / Rejected Hypotheses
- Critical Unknowns
- Non-Introspectable Unknowns
- Provider-Level Questions
- Execution-Level Questions
- Experiments Pending
- Evidence Gaps
- Decisive Dependencies
- Confidence
- Next Information-Gathering Action
- Last Checkpoint

Current state is mutable.

## Case Lifecycle

Statuses:

```text
active
paused
awaiting-evidence
closed
reopened
superseded
```

Closed does not mean permanently immutable.

## Resume and Recovery

The chat session is not the authoritative case container.

When the workspace exists:

> Workspace case state is the continuation authority.

Resume procedure:

1. discover root;
2. read index;
3. resolve target case;
4. read case state;
5. read relevant supporting artifacts;
6. create resume checkpoint;
7. continue from current frontier.

Do not restart the interview.

Persistence cannot survive deletion of both conversation history and workspace without backup.

## Case Persistence

Persist substantive, long, research-heavy, hypothesis-heavy, experiment-driven, or cross-session cases.

Update case state after meaningful state changes, not every trivial turn.

## Current State vs Historical Record

Rule:

> Current state is mutable.
> Historical evidence is append-only or explicitly superseded.
> Historical conclusions are versioned.
> History must never be silently rewritten.

## Conclusion Versioning

Use versioned conclusions for materially revised or reopened cases.

Keep `conclusion.md` as current synthesis or pointer.

Do not rewrite old reasoning as though later evidence had always been known.

## Decision Log

Complex cases should record:

- date;
- conclusion version;
- decisive reasons;
- changed evidence;
- reopen triggers;
- supersession.

## Canonical Memory

Suggested record:

```yaml
id: schedule-0042
type: fact
value: "User can reliably allocate one weekend session per week."
source_cases:
  - 2026-08-19_choose-long-term-sport
observed_at: 2026-08-19
valid_from: 2026-08-19
valid_to: null
confidence: high
scope:
  - recurring-activities
stability: contextual
status: active
supersedes: []
conflicts_with: []
review_after: 2027-02-19
```

Types:

```text
fact
preference
behavior
hypothesis
```

Statuses:

```text
active
superseded
retracted
disputed
expired
```

Never silently promote hypothesis to fact.

## Cross-Case Retrieval

Use retrieval, not preload.

Reuse old facts only if relevant and fresh.

Use old preferences as contextual priors.

Use old behavior as evidence, not destiny.

Use old hypotheses only to generate new hypotheses.

Do not transfer old recommendations across domains.

## Truth Maintenance

Classify new-vs-old relationships:

```text
confirm
refine
contextualize
temporal-update
supersede
contradict
invalidate
retract
```

Do not immediately overwrite.

Temporal change is not contradiction.

Context difference is not contradiction.

Real contradictions require provenance comparison and explicit retraction / dispute when appropriate.

Rejected hypotheses should retain revision history.

Unresolved conflicts remain disputed.

## Cross-Case Impact Analysis

Trigger when:

- important cross-case fact changes;
- high-confidence behavior record changes;
- decisive hypothesis is invalidated;
- major constraint changes;
- old record is retracted.

Pipeline:

```text
new evidence
  -> classify relationship
  -> update canonical state
  -> identify dependent cases
  -> estimate material impact
  -> reopen or annotate
```

Do not reopen every historical case after trivial changes.

## Dependency Tracking

Conclusions may reference:

```text
M: canonical memory
E: case evidence
H: hypothesis
X: external evidence
```

Goal:

> Which conclusions depended on this record?

## Interaction Budget

Quick: roughly 3–6 substantive questions.

Standard: roughly 6–12.

Deep: use information value, fatigue, and time; a 30–60 minute equivalent window may be an early reassessment point.

Budget is a ceiling, not a quota.

## Mandatory Checkpoints

Run after roughly 5–8 substantive user answers, major constraints, hypothesis reversals, scope expansion, budget boundaries, low-value psychological drift, resume, and before complex closure.

Checkpoint asks:

- what problem are we solving;
- whether framing changed;
- current success criteria;
- decisive facts;
- strengthened / failed hypotheses;
- top unknowns;
- highest decision sensitivity;
- best next evidence source;
- recommended action if stopping now;
- whether another question can change it;
- whether action now has greater information value;
- whether new evidence affects another case.

## Evidence Routing

ASK when user knows the private/experiential answer.

RESEARCH when the answer exists externally.

INSPECT when behavior, records, files, calendars, logs, or historical evidence is stronger.

INFER cautiously from existing evidence.

TEST when reality can answer better than introspection.

## Question Admission Gate

Before asking verify:

- unknown;
- decision-sensitive;
- user is best source;
- reliably answerable;
- no stronger behavior/document evidence;
- no better experiment;
- relevant rather than merely interesting.

Approximation:

> Information Value ≈ Decision Sensitivity × Current Uncertainty × Evidence Reliability ÷ Acquisition Cost

## "I Don't Know"

Memory unknown -> stop weak reconstruction.

Prediction unknown -> TEST.

External-fact unknown -> RESEARCH.

Problem-definition unknown -> explore.

Conditional unknown -> identify condition if action-sensitive.

Do not repeatedly rephrase predictive unknowns.

## Evidence Hierarchy

1. Hard constraints and direct reality.
2. Observed behavior.
3. Environment and opportunity structure.
4. Repeated preferences and motivational patterns.
5. Analogies and interpretive clues.
6. Generic population research.

Do not use population research to create false individual precision.

## External Research

Research only when it reduces meaningful uncertainty.

Prioritize current local resources, prices, schedules, regulations, eligibility, medical/professional standards, provider quality, real progression paths, and market conditions.

Evidence grades:

- A: current authoritative / first-party;
- B: recent independently corroborated;
- C: aggregator / stale / generic;
- D: unverified anecdote.

Do not present C/D as confirmed fact.

## Provenance and Freshness

Important evidence should preserve source, date, valid time, confidence, type, scope, inference status, and review date.

Recheck stale-prone facts.

## Avoid Personality-Test Logic

Do not map introversion, extroversion, competitiveness, analytical style, creativity, or discipline directly to domain recommendations.

Prefer behavior, constraints, reward structure, opportunity structure, environment, and failure modes.

## Preference Is Not Tolerance

Distinguish:

- can tolerate;
- likes;
- can sustain.

## Context Dependence

Investigate whether persistence depended on school, work, partner, location, community, institutional schedule, or accountability.

## Intention–Behavior Gaps

Investigate startup friction, missed time windows, all-or-nothing responses, decision fatigue, easy cancellation, weak accountability, unstable context, overplanning, and oversized minimum actions.

Do not moralize.

## Competing Hypotheses

Maintain multiple plausible explanations for ambiguous problems.

Seek discriminating evidence.

Record rejected hypotheses rather than silently replacing them.

## Reversibility and Option Value

Prefer low-cost, reversible, information-rich actions before expensive, irreversible, low-information commitments.

Treat small actions as purchases of information.

## Real-World Experiment Design

Specify:

- what to do;
- what not to substitute;
- what to observe;
- what to ask others;
- how to compare;
- whether novelty requires repetition.

Do not merely say "try it and see."

## Stop Conditions

Stop when:

- remaining unknowns cannot change action;
- action remains stable under opposite answers;
- next critical unknown is non-introspectable;
- experiment is better;
- research has reached practical limit;
- more questions mainly complete the user profile;
- investigation cost exceeds information value;
- user fatigue rises without gain;
- conversation drifts into irrelevant detail.

## Conclusion Levels

Separate:

- descriptive;
- explanatory;
- strategic;
- immediate action.

They may have different confidence.

State reversal conditions.

## Reopen Option Space

Do not force a winner among bad initial options.

Allow none, third option, hybrid, delay, environment change, or upstream constraint resolution.

## High-Stakes Constraints

Identify health, safety, legal, financial, and other high-stakes constraints early.

Separate general guidance from individualized professional evaluation.

## Privacy and Data Minimization

Request and persist only minimum necessary detail.

Do not save sensitive information merely because it was mentioned.

## Case Closure

At closure:

- update state;
- set status;
- update conclusion;
- version when appropriate;
- record decisive factors;
- separate facts and hypotheses;
- record unknowns;
- record reversal conditions;
- record next action;
- record reopen trigger;
- update index.

## Case Reopening

Reopen for experiment results, changed constraints, new external evidence, resolved unknowns, or material cross-case changes.

Read current state first.

Do not restart interview.

Version materially changed conclusions.

## Final Governing Principle

Adaptive life consulting is a persistent evidence-aware system for disciplined uncertainty management in service of action.

Ask only when the answer may change belief or action.
Research what can be checked.
Prefer behavior over abstract self-description.
Do not force users to predict unfamiliar experiences.
Test what reality can answer better.
Treat the workspace, not chat, as the durable case container.
Keep current state mutable and history traceable.
Distinguish time change, context difference, and contradiction.
Never silently overwrite material history.
Propagate only material cross-case changes.
Retrieve selectively.
Separate immediate-action confidence from long-term-conclusion confidence.
Stop when reality can produce the next better evidence.
